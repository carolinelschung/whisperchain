# WhisperChain+ Threat Model

## Overview
WhisperChain+ is an anonymous encrypted messaging system with role-based access control (RBAC). Its security goals are to protect message confidentiality, preserve Sender anonymity, enforce authorization and token limiting, and provide accountability through an append-only audit log and moderation system. This threat model identifies potential attacks against the system, the defenses implemented to reduce those threats, and the risks that still remain. The defenses and residual risks below describe the system as built, and the demo and tests in this repository exercise them.

## Threat Analysis
| Threat | Defense | Residual Risk |
|---|---|---|
| **Compromised Admin:** An attacker gains access to an Admin account and uses its permissions to manipulate users, roles, and rounds. | Enforce authentication and RBAC on every administrative endpoint, with access denied by default. Admins have no access to message contents, private keys, or the audit log. An Admin cannot change their own roles, so they cannot quietly make themselves a Moderator. Role changes and round advances are recorded in the append-only audit log. | An attacker with a compromised Admin account can still make unauthorized changes. They can change other users' roles, including promoting an account to Moderator, who can read flagged messages. They can also advance the round, which invalidates every unspent token. The log records the new roles but not whose roles changed, and accounts created with the `create_admin.py` script are not recorded in the log. Audit logging helps detect these actions but does not prevent them. |
| **Shared or stolen anonymous token:** Someone obtains another user's token and uses it to submit a message without the intended Sender's permission. | Generate tokens using a cryptographically secure random number generator (Python's `secrets` module, 256 bits). Store only token hashes on the server. Accept each token only once, and reject spent, invalid, frozen, or out-of-round tokens. A token is only valid in the round it was issued for, so advancing the round expires every unspent token. | A stolen token can be used by whoever obtains it first, until it is spent or the round ends. Because tokens are intentionally unlinkable to user identities, the server cannot reliably determine who originally possessed or used a particular token. The server does not use HTTPS in the demo, so a token sent over a network could also be read and used by an eavesdropper (see the network eavesdropping row). |
| **Nonrepudiation:** A Sender denies having submitted a message, or the system cannot establish whether a message was authorized. | Require a valid anonymous token for each message submission. Record timestamped submission events in the audit log without recording the Sender's identity. Each log entry is signed by the system, so the record that a token was used cannot be quietly changed. | The system can demonstrate that a valid token was used to submit a message, but cannot prove which individual sent it, because messages are not signed by the Sender. This is an intentional tradeoff: strong attribution to a person would undermine Sender anonymity. |
| **Deanonymization through metadata or timing:** An attacker correlates token issuance, message submission, timestamps, or other metadata to infer a Sender's identity. | Store token hashes separately from the records indicating which users received tokens, and keep no user id in the token table. Do not associate Sender identities with submitted messages. The audit log records only the event, the timestamp, and the role, never a username, user id, or IP address. | The log timestamps can still leak information. In the sample log, a `token_issued` event and the following `message_sent` event occur in the same second, so in a small group an observer could match them. Role strings such as "Moderator,Recipient,Sender" can also narrow down which account an event came from. A malicious or compromised server could record who requests each token and when. Network metadata, such as IP addresses, is visible to the network and the server. The design reduces linkability but does not guarantee anonymity against a server that deliberately collects identifying metadata. |
| **Spam or flooding:** A user or attacker submits excessive messages, creates multiple accounts, or attempts to overwhelm the system. | Enforce one anonymous token per Sender per round and one message per valid token. Reject reused tokens. Require passwords of at least 15 characters, and hash them with a slow, salted algorithm (PBKDF2-HMAC-SHA256, 600,000 rounds). Five failed logins in a row raise an alert in the audit log. | An attacker may create multiple accounts, since Sender and Recipient registration is open, and use each one's token to bypass per-account limits. There is no rate limiting or account lockout on login. The failed-login alert is system-wide and only writes a log entry, so it does not block anything. |
| **Audit log tampering:** An attacker modifies or deletes audit records to hide unauthorized activity or make moderation actions difficult to investigate. | Maintain an append-only, timestamped audit log. Use a cryptographic hash chain so that modifying or removing an existing entry changes the hashes of subsequent entries. Digitally sign audit log entries to provide an additional layer of integrity verification. The Moderator can check the whole chain with `GET /audit/verify`, and the tests confirm that editing or deleting a record in the middle of the log is detected. | The hash chain and signatures make modification detectable but do not prevent it. Deleting the newest records (truncating the end of the log) is not detected, because the remaining chain is still valid. The signing key is stored on the same server as the database, and its password defaults to a demo value unless one is set in the environment. If an attacker gains access to the signing key, they could alter audit entries and generate valid signatures for the modified records. |
| **False flagging:** A Recipient intentionally flags a harmless or legitimate message, or alters its content, to cause unnecessary moderation. | Only allow Recipients to flag messages in their own inbox. Require Moderators to review flagged messages before taking action. Record flagging and moderation decisions in the audit log. Raise an alert in the log when 3 messages are flagged in the same round. | A Recipient can still submit dishonest flags, creating unnecessary work for Moderators. Because the Recipient encrypts the flagged copy for the Moderator, nobody can verify that it matches the original message, so a dishonest Recipient could fabricate its content. The alert only writes a log entry and does not block anything. Human review reduces the risk of inappropriate action but cannot eliminate biased or incorrect moderation decisions. |
| **Limits of token freezing:** A Moderator freezes the token of an abusive message and expects the abusive Sender to be stopped. | Freezing marks the flagged message's token as frozen and records a `token_frozen` event in the audit log. Only flagged messages can be frozen. | Freezing does not stop the Sender from sending again. By the time a message is flagged its token is already spent, and the Sender's next token is unlinkable to the old one. Freezing is a record of abuse, not a block. Stopping a repeat abuser would require linking tokens to identities, which would break anonymity. This is the central tradeoff between privacy and accountability in the design. |
| **Network eavesdropping:** An attacker on the network reads or replays traffic between the client and the server. | Message contents are end-to-end encrypted (AES-256-GCM, with the key wrapped by RSA-OAEP), so the server and the network only see ciphertext. Session tokens are stored on the server only as hashes. | The demo runs over plain HTTP on localhost. Login passwords, session tokens, and anonymous tokens travel unencrypted, and an eavesdropper could read or replay them. A real deployment would need HTTPS (TLS). |
| **Stolen session token or database dump:** An attacker gets a user's session token, or a copy of the server's database. | Passwords are stored only as salted PBKDF2 hashes, and session tokens only as hashes. A database dump contains no plaintext messages, no sender column, and no usernames in the audit log, and the tests check this. | Sessions never expire. A session stays valid until the user logs out, so a stolen session token works until then. |
| **Compromised or curious server operator:** The person running the server tries to break anonymity or read messages. | The token table has no user id and the issuance table holds no token, so the stored data does not link a Sender to a message. Messages are stored only as ciphertext encrypted to the Recipient's public key. | The anonymity of tokens relies on the server not logging the link between a user and the token it issued. A server that records this at issuance time could unlink every message. This is a trust assumption of the design, not something it can enforce. |
| **Moderator private key stored on the server:** Someone with access to the server's files reads the flagged messages meant only for the Moderator. | The server code never decrypts flagged copies. The Moderator's private key file is protected by a password. | `create_admin.py` generates the Moderator's keypair on the server and saves the private key there (`keys/<username>_private.pem`). Anyone with the server's files and the key password can read every flagged message, so the key's protection depends on that password. |

## Conclusion
The system uses encryption, anonymous tokens, RBAC, moderation, and tamper-evident logging to address its primary security threats. These defenses reduce the likelihood and impact of attacks, but do not eliminate all risks. In particular, compromised privileged accounts, metadata correlation, stolen tokens, the lack of HTTPS in the demo, the Moderator's key being stored on the server, and sufficiently powerful attacks against the audit infrastructure remain important limitations. Freezing a token records abuse but cannot stop a repeat offender, which is a deliberate cost of keeping Senders anonymous.
