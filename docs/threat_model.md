# WhisperChain+ Threat Model

## Overview
WhisperChain+ is an anonymous encrypted messaging system with role-based access control (RBAC). Its security goals are to protect message confidentiality, preserve Sender anonymity, enforce authorization and token limiting, and provide accountability through an append-only audit log and moderation system. This threat model identifies potential attacks against the system, defenses already implemented to reduce those threats, and the risks that still remain.

## Threat Analysis
| Threat | Defense | Residual Risk |
|---|---|---|
| **Compromised Admin:** An attacker can gain access to an Admin account and use its permissions to manipulate users, roles, public keys, and other system elements |  Enforce authentication and RBAC on administrative endpoints. Never give Admin access to private keys or message contents. Record Admin actions in append-only audit log. |  An attacker with a compromised Admin account can still make unauthroized changes. Audit logging can help detect these actions but does not prevent them.
| **Shared or stolen anonymous token:** Someone obtains another user's token and uses it to submit a message without the intended Sender's permission. | Generate tokens using a cryptographically secure random number generator. Store only token hashes on the server. Accept each token only once and reject spent, invalid, expired, or frozen tokens. | A stolen token can be used by whoever obtains it first. Because tokens are intentionally unlinkable to user identities, the server cannot reliably determine who originally possessed or used a particular token. |
| **Nonrepudiation:** A Sender denies having submitted a message, or the system cannot establish whether a message was authorized. | Require a valid anonymous token for each message submission. Record timestamped submission events in the audit log without recording the Sender's identity. | The system can demonstrate that a valid token was used to submit a message, but cannot prove which individual sent it. This is an intentional tradeoff: strong attribution to a person would undermine Sender anonymity. |
| **Deanonymization through metadata or timing:** An attacker correlates token issuance, message submission, timestamps, or other metadata to infer a Sender's identity. | Store token hashes separately from records indicating which users received tokens. Do not associate Sender identities with submitted messages or include them in audit logs. Minimize collected metadata and restrict access to server logs. | A malicious or compromised server could record the timing of token issuance and message submission and attempt to correlate them. Network metadata, such as IP addresses, may also reveal information. The design reduces linkability but does not guarantee anonymity against a server that deliberately collects identifying metadata. |
| **Spam or flooding:** A user or attacker submits excessive messages, creates multiple accounts, or attempts to overwhelm the system. | Enforce one anonymous token per Sender per round and one message per valid token. Reject reused tokens. | An attacker may create multiple accounts or distribute activity across multiple accounts to bypass per-account limits. 
| **Audit log tampering:** An attacker modifies or deletes audit records to hide unauthorized activity or make moderation actions difficult to investigate. | Maintain an append-only, timestamped audit log. Use a cryptographic hash chain so that modifying or removing an existing entry changes the hashes of subsequent entries. Digitally sign audit log entries to provide an additional layer of integrity verification and help detect unauthorized modifications. Restrict write access to the logging functionality. | Although the hash chain and digital signatures make unauthorized modifications detectable, they do not prevent an attacker with sufficient server privileges from tampering with the log. If an attacker gains access to the signing key, they could potentially alter audit entries and generate valid signatures for the modified records.|
| **False flagging:** A Recipient intentionally flags a harmless or legitimate message to cause unnecessary moderation or freeze another user. | Only allow Recipients to flag messages in their own inbox. Require Moderators to review flagged messages before taking action. Record flagging and moderation decisions in the audit log. | A Recipient can still submit dishonest flags, creating unnecessary work for Moderators. Human review reduces the risk of inappropriate action but cannot eliminate biased or incorrect moderation decisions. |

## Conclusion
The system uses encryption, anonymous tokens, RBAC, moderation, and tamper-evident logging to address its primary security threats. These defenses reduce the likelihood and impact of attacks, but do not eliminate all risks. In particular, compromised privileged accounts, metadata correlation, stolen tokens, and sufficiently powerful attacks against the audit infrastructure remain important limitations.
