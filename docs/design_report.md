# WhisperChain Security Design Report

## Overview
WhisperChain+ is a messaging system that preserves anonymity. As a result, most of our design decisions were the result of balancing the tradeoff between anonymity and accountability. The messaging platform supports four roles: Senders write messages, Recipients read and can flag messages, Moderators review flagged messages and freeze tokens, and Admins manage users and roles but never see content.

## Architecture
The server is Python with FastAPI and stores everything in SQLite. The client is a command line program that talks to the server through HTTP endpoints, and both sides share one crypto module. A Sender logs in, asks for a token, looks up the Recipient's public key, encrypts the message on their own machine, and submits it with only the token and no login. The Recipient later logs in and reads their inbox. The server only ever stores ciphertext, so it never sees an unencrypted message.

The database handles a lot of privacy functionality. The token_issuance table records that a user receives a token during a round, without linking that specific user to the token. That way, when a message is sent using that token, the sender remains anonymous. The valid_tokens table holds token hashes without storing user information, for the same reason. The messages table contains a random id, the recipient, a hash of the anonymous token (so that a Moderator can freeze it later), and the encrypted data (again, no sender column). Nothing in the database directly connects a message back to a person, but it is possible that it could be inferred in certain cases, like if only one user and token are active. 

## Cryptographic Choices

Messages use symmetric AES-256-GCM encryption, and the AES key gets wrapped with the Recipient's RSA public key (2048 bit, OAEP with SHA-256). As we have discussed in class, we used a hybrid setup because we wanted the public-private key functionality of RSA while also achieving the more efficient encryption/decryption of symmetric encryption. Only the Recipient's private key can unwrap the AES key, which makes it end-to-end encrypted, so even a stolen database doesn't show message contents.

Passwords are salted with a random 16 byte salt and hashed with PBKDF2-HMAC-SHA256 at 600,000 rounds, and we require at least 15 characters. The slow hash makes guessing expensive if the database leaks, so we’re more protected against brute force attacks. Session tokens and message tokens are random 32 byte values and we only store their SHA-256 hashes, so a database dump wouldn’t reveal a usable token.

The audit log is a hash chain to make tampering easily detectable. Each entry's hash is SHA-256 of the previous hash plus the entry, and each hash is signed with the system's RSA key. That key is generated the first time the server needs it and then saved to a password-protected file, so it stays the same across restarts. Editing or deleting a record breaks the chain, and the signature means someone can't just recompute all the hashes without the key. Encrypted data goes between the client and server as Base64 text, while the server's own tokens, ids, hashes and log signatures are stored as hex.

## Access Control
Every protected endpoint calls one function, require_permission, which determines who the caller is from their session token. From there, require_permission loads the caller’s roles from the database and determines whether any of the roles has the necessary permission. If no permission matches, the request gets a 403 error; a missing or bad login gets a 401 error. This precaution aims to achieve the complete mediation from class, since the only endpoints that skip the login check are register, login, and message submit (and submit is authorized by the anonymous token instead). Roles are read from the database on every request, so a role change can take effect right away.

We also built in separation of duties functionality. An Admin can assign roles and advance the round, but can’t access the inbox, the flag queue, and the audit log. An Admin also can't change their own roles, so they can't make themselves a Moderator. A user can only register themselves as a Sender and/or Recipient. Admin and Moderator accounts have to be made by a script on the server or by an Admin. A user can hold more than one role and gets the combined permissions (ex. Be both a Sender and Recipient). We wrote tests that try every role against every protected endpoint [tests/test_rbac.py, docs/rbac_matrix.md].

## Tradeoffs Between Privacy and Accountability
As we have mentioned, tokens enforce privacy. When a Sender asks for a token, the server saves the fact that a user got a token for the round in one table and the token’s hash in a different table with no id. This protocol means that each user only gets one token per round, but the token can’t be tied to them by looking at the data. Messages are submitted using only the token and no identifying user information. The audit log records the time, the action, and the role, but never a username, IP, or message content. Even failed login attempts are logged without a username. We designed the system so that within the raw database file and the log there is never plaintext, there are no sender columns, and usernames don't appear in the log.

For accountability, when a Recipient flags a message, their client re-encrypts it using the Moderator’s public key and sends it. This means that the Moderator can read flagged messages, but no other messages. The Moderator can also then freeze the token that sent it. The system writes an alert to the log when 3 messages are flagged in one round or when 5 failed logins happen in a row. The signed hash chain lets a Moderator run a check and see if anyone changed the log, and our tests edit and delete a log row to confirm the check catches both.

The tradeoff between privacy and accountability is especially present with freezing. By the time a message gets flagged, its token is already spent. Since only one token can be used per round, this means that freezing doesn’t really stop anyone and serves more as a record of abuse. Since Senders must remain anonymous, there is no way to freeze the user associated with a message. This is the tradeoff of keeping senders anonymous, because the server can't look up who owns a token in order to ban them from an account level.

## Limitations
We think that the biggest limitation is that all of this depends on the server not logging the link between a user and a token. If the server did that, then all anonymity is gone. In this situation, the mission critical goal is to protect confidentiality. The second is timing. The log has timestamps, and token issued and message sent are both logged, so on a small system with a small population of active Senders someone reading the log could probably match them up. 
Another limitation that we discussed is the server also can't tell if a flag is honest. The way we designed the system, the Moderator's copy is built on the Recipient's device, and the server doesn’t check if it matches the original. Because of this, a dishonest Recipient could write a fake message, encrypt it for the Moderator, and flag it, and the server would store it without being able to verify if it matches the message that Recipient received in the first place. Also, the log is signed with a key that lives on the same server, and its password defaults to a demo value unless an environment variable is set. This is something we discussed in lecture where it’s always best practice as a part of hardening to change default passwords because whoever controls the server could read the key, edit the log, and re-sign everything, and the check would still pass. The log check also only proves the records that exist are consistent. If someone deleted the newest records off the end of the log, like a recent alert, nothing would point at the gap and it wouldn't get caught. There are a few smaller limitations we considered as well, like that sessions only end at logout with no timeout functionality and that alerts only write to the log, don't block anything, and require human review. 


## Conclusion
Overall we tried to preserve confidentiality by making it so that the design keeps message content and sender identity away from the server and the admin, while still giving Moderators a way to review and record abuse. It doesn't solve everything, anonymity really depends on trusting the server not to log the link between a user and their token.
